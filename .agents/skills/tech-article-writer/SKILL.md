# tech-article-writer

目标：让搜这个问题的人搜得到、点进来读得懂、读完愿意转发，同时每条事实都有出处。全流程见 `docs/pipeline.md`，写作说明见 `docs/writing-agent.md`，写法样本见 `docs/style-reference.md`，SEO 规则见 `docs/seo-distribution.md`，标题、封面和开头见 `docs/title-cover-intro.md`。

中间文件放私有工作区 `../engineering-notes-workbench/`：简报在 `briefs/`，草稿在 `drafts/`，核查和读者测试在 `verification/`，平台标题和 X 串推在 `distribution/<slug>/`。

## 默认读者

用过 Claude Code、Cursor、Copilot 等 AI 编程工具的开发者和技术爱好者，听说过 Agent，没读过 Agent 框架源码。目标是这类读者里 80% 能读懂，同时不觉得被讲浅了。作者指定其他读者时按作者的来。

读者熟悉的开发词直接用，不解释：Issue、PR、CI、分支、worktree、会话、提示词、API、重试。

## 步骤

1. **搜索词研究**。动笔前做，结果写进 `briefs/<slug>.md` 的关键词表：
   - 中英文种子词各 2–3 个，取 Google 和百度联想词（接口见 `docs/seo-distribution.md`），记下取词日期。
   - 看搜索结果第一页已有什么、缺什么。
   - 定 1 个主关键词、2–4 个相关词，标出每个词对应的搜索意图（是什么 / 原理 / 怎么用 / 对比）。
   - 有同名干扰（例如别家产品也叫这个名字）时，主关键词要带上区分词。
   - 做讲法菜单（规则见 `docs/title-cover-intro.md`），发给作者选。作者选定前不写简报。
2. **定读者和一句话**。写进简报：读者、读完能复述的一句话、读者关心的 2–3 个问题。这些问题优先从第 1 步的搜索意图里选。写不出这句话时先问作者，不自己补。
3. **写 300 字短版**。第一句是发生了什么或读者为什么该关心，接着是难点，最后是结论。短版讲不清，说明题目太大，回到第 2 步缩小。存为 `distribution/<slug>/x-short.md`。
4. **扩写长文**。先读 `docs/style-reference.md`，再写 `drafts/<slug>.md`：
   - **SEO 落点**：标题和 H1 前半段含主关键词；描述 80–120 字含主关键词；首段前 100 字说清“它是什么、能干什么”并出现主关键词；2–3 个小标题同时是读者问题和相关搜索词，例如“DeepSeek SuperAgent 是什么”。不堆词，同一个词在正文里自然出现即可。
   - **用真实例子**：真实的使用场景、源码里的规则、配置和数字。不用生活类比替代技术本身；真实例子讲不清时，才用同一技术领域里读者熟悉的东西作对比，例如“和 GitHub Actions 的重试一样”。按文档推演的场景要说明是推演。
   - **概念**：通用开发词直接用；项目自造的概念第一次出现时写成“中文名（英文原名）”，紧跟一句话说明它在项目里管什么。
   - **链接**：关键源码、文档链接放在对应句子旁边；其余放文末“源码对照”。
   - 边界集中写在一个“用之前要知道的”小节，只写会改变读者判断的内容。
   - 结尾给开发者能带走的做法。
5. **幕后核查**。把正文里每条事实列成表，写进 `verification/<slug>.md`，每条附出处（文件和行号、测试报告、链接）。查不到的删掉或交给作者。核查过程不搬进正文。
6. **读者测试**。开一个没有上下文的子 Agent，告诉它“你用 Claude Code 或 Cursor 写代码，没读过 Agent 框架源码”，只给它正文。让它：用一句话复述文章；回答第 2 步列的问题；标出读不懂的段落，以及讲得太浅、想跳过的段落；说出它会用什么词搜到这篇。复述对得上、没有卡住的段落、也没有被评为太浅的主体段落，才算通过。不通过就改稿再测，记录写进 `verification/<slug>-reader-test.md`。
7. **标题、封面、开头和平台版本**。先读 `docs/title-cover-intro.md`。讲法在第 1 步之后已经由作者从菜单里选定（菜单最多 4 个，第 1 个用原说法，推荐一个并写理由）；这里按选定讲法定稿：
   - 网站标题 3 个候选，主关键词靠前，30 字以内；描述 1 段。
   - 掘金、知乎、CSDN 标题和 X 首句，按平台分工改写，只在平台、读者或搜索词不同时才改。
   - 封面文字 1 套：默认 3 行，每行最多 6 个字，写完连起来读一遍查主语。
   - 检查开头：前 100 字含主关键词并说清它是什么；第一句给读者关心的事和作者的依据。
   - 按兑现检查表逐项过，结果写进 `distribution/<slug>/title-cover-intro.md`。
   - 掘金、知乎、CSDN 用和网站相同的正文，不单独改写；只准备各平台标题和文末一行“首发于 <网站链接>，示例代码见 <仓库链接>”，并把站内相对链接换成完整地址。
   - X 串推由第 3 步的短版改成，读 `~/.codex/skills/x-native-writer/SKILL.md`，最后一条放文章链接。
8. **发布前检查**，命令和结果附在核查文件末尾：
   - 对照简报关键词表，逐项确认标题、H1、描述、首段、小标题的落点。
   - `python3 /tmp/fenng-style/scripts/lint_copy_rules.py <文件>`。没有这个目录就先 `git clone https://github.com/Fenng/tech-doc-style-chinese /tmp/fenng-style`。忽略直角引号提示，本项目用弯引号。
   - `npx -y autocorrect-node --lint <文件>` 和 `npx -y @lint-md/cli <文件>`，修到 0 个 error。
   - 对照 `~/.gemini/dbskill/skills/dbs-ai-check/SKILL.md` 的特征清单过一遍，只改明显的 AI 腔。
   - 涉及公司、他人或敏感话题时，再用 `~/.gemini/dbskill/skills/dbs-content-risk-check/SKILL.md` 查一次。

## 规则

- 不编造经历、实验、数字、引用、运行记录和作者没表达过的观点。
- 区分“代码和文档是这么写的”和“我测过”。没测过就在边界小节说一次。
- 没有工具结果，不写“已核实”。
- dbs 系列 skill 只作检查清单和参考，不按它们的模板写。
- 不发布、不提交、不发帖。发布由作者按 `docs/sop.md` 手动做。
