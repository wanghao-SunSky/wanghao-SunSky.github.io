讨论 Subagent 怎么用，先看一个跨模块排障场景。让单个 Agent 排查线上问题，常常会在半路跑偏。为了定位根因，它连续做十几轮全局搜索，读进几千行构建日志和报错堆栈。等终于翻到可疑文件、准备动手改代码时，主对话的上下文窗口已经被大段原始输出塞满，最开始交代的接口兼容条件反而退到了注意力边缘，改着改着就开始顾此失彼。

把“查调用链、筛日志”这类过程很吵的支线拆给 Subagent（子智能体），瞄准的就是这个问题：Subagent 带着只读工具在独立的上下文窗口里翻找代码，最后只把十几行结论和文件路径交回主会话，主 Agent 拿着干净的摘要继续写代码。

顺着这个甜头往下走，不少团队会把系统按职能越拆越碎：意图路由一个 Agent、拆解计划一个 Agent、前后端各配一个专家 Agent，最后再加一个汇总 Agent。Anthropic 在 2026 年 10 月的一篇工程复盘里专门讨论过这类过度拆分：在部分企业系统里，把独立的路由、规划和领域专家重新合并回主循环，改用按需加载的 skills 和工具扩展能力，系统反而更稳、更好维护；遇到可测量的上下文膨胀、真正互不依赖的并行工作，或者工具选择与系统指令冲突时，仍值得保留或测试 Subagent。

想把 Subagent 用在刀刃上，与其照着框架文档堆角色，不如顺着实际开发链路想清楚五件事：什么时候该拆、上下文怎么交接、为什么代码审查和疑难会诊要反着传信息、多人改代码怎么避开隐含冲突，以及运行时的权限和恢复底线在哪里。

## 什么时候该拆，什么时候留在主循环

要不要拆出 Subagent，首先看子任务之间是不是前后咬死的。

如果下一步怎么走高度依赖上一步翻出来的细节——比如先顺着报错定位数据流，发现是上游序列化格式变了，再顺藤摸瓜去核对消费端的兼容逻辑——留在单个主循环里串行推进往往最顺。一旦硬拆给多个角色接力，每次跨边界传递摘要都会丢掉中间细节；为了补齐背景，又不得不把大段上下文来回拷贝。已有实验和工程复盘显示，任务结构会影响拆分的收益：子问题彼此独立时，中心协调下的并行拆分可能提效；换成强依赖的连续决策，多加一层委派反而容易拉低表现，工具调用越密集，额外的协调损耗越重。

成本和耗时也得算实账。并行拉起三个只读分支确实能缩短用户的体感等待时间，整次运行的耗时仍然卡在“任务拆解 + 最慢分支 + 汇总校验”上。总成本则未必随等待时间一起下降，因为每个 Subagent 都要单独携带系统提示词、任务背景和各自的工具返回结果。遇到步骤固定、规则明确的流程——比如“把仓库里 30 个模块逐个扫一遍配置项，一个都不能漏”——直接用普通代码写循环、在循环内部按步调用 Agent 更可靠；如果交给主模型自己在对话里决定调几次 Subagent，模型很容易漏扫几个目录就提前收尾。

放到日常开发里，真正值得拆出 Subagent 的场景通常有四类：

- **过程输出很大、结论却很短的只读探索**。比如跨十几个目录查历史调用点、从长日志里筛异常时间线，或者同时检索几份互不相关的技术文档。就算两个分支搜重了一小部分，主 Agent 合并时去重即可，不会改坏仓库。
- **工具集或指令存在冲突**。挂在同一个 Agent 上的工具太多时，模型选错工具的概率会上升；不同任务的系统指令也可能互相牵制。给检索分支只留读文件和搜索工具，拿掉写库、发版和外部通知能力，既收敛了风险，也能减少工具干扰。
- **需要刻意切换上下文视角**。典型情况是编码完成后的独立审查，需要避开编写时的试错轨迹。
- **按难度分层调用模型**。常规文件搜集交给响应快、单价低的模型处理，卡在复杂推理时再把现场交给更强的模型协助诊断。

动手拆分前，建议先把单 Agent 配上按需加载的上下文与工具跑通基准任务。确认主循环确实撞上了上面这几类瓶颈，再针对具体环节拆出 Subagent，排查问题时也清楚多出来的复杂度换回了什么。

## 派活与转交：上下文到底传多少

定下要拆之后，紧接着就会碰上控制权怎么走的问题。表面上都是多个 Agent 配合，落到运行机制上其实是两条完全不同的路。

开发工具里最常见的是**中心委派**：主 Agent 始终握着对话控制权，对最终结果负责，把边界清楚的子任务当成一次函数或工具调用派给 Subagent，拿到返回摘要后再核对、汇总。比如升级仓库里的鉴权库时，主 Agent 同时派出两个只读 Subagent，一个查现有中间件怎么处理过期 token，一个查测试目录里的 mock 辅助函数，收齐两边定位到的文件路径后再统一改代码。用这种模式时有一个容易忽略的细节：如果自定义 Subagent 的角色说明长期常驻在主会话提示词里供主模型挑选，说明写得太啰嗦同样会挤占主上下文。

另一条路是**控制权转交（Handoff）**，多见于分诊和客服流程：入口节点判断清诉求后，直接把当前会话移交给账单或退改签专员继续接待。转交模式最容易踩坑的地方，是默认以为“换了个 Agent 就等于隔开了历史”。很多框架在转交后默认让下游看到此前的完整对话，即便加了消息过滤，早先普通回复里已经复述过的敏感字段也不会自动消失；入口节点配置的输入检查未必会自动覆盖最后一个发言的节点，模型开启并行工具调用时甚至可能在一轮里同时触发两次转交。只要业务要求严格的上下文隔离，直接另起一次干净运行、只传入必要字段，通常比在原会话上做转交更稳妥。

回到最常用的中心委派，很多团队第一次接 Subagent 时效果不好，症结往往出在派活指令太含糊。主 Agent 只丢过去一句“去查查订单模块的权限问题”，子分支不知道查到哪一步算完，有的顺着无关引用越翻越远，有的找不到线索就在原地反复搜索，几个并行分支还可能扎堆去读同一批文件。

想让 Subagent 稳定交活，派发下去的任务包需要把边界钉死：

1. **要回答的具体问题与禁区**：写明这次只查什么，哪些目录、配置或共享接口不准碰。
2. **代码快照与已敲定的前提**：带上当前分支、关键文件路径和主会话已经确认的设计约束；如果主分支代码已经往前改了，基于旧快照跑出来的结论要能识别出来。
3. **工具范围与停止条件**：限制可用工具、最大调用步数和超时时间；一旦发现实际情况与既有假设冲突，停下来上报，别自己硬改方向。
4. **可核对的返回格式**：把查实的结论、源码依据（文件路径加行号）和没查清的疑点分开列明。

主 Agent 收到返回结果后，也不能光看格式工整就直接采信。在不少多角色示例里，上游节点看到下游返回一句“已核实无误”就放行了；真正在工程里落地时，主 Agent 或校验脚本至少要去核对引用的文件行号和文档内容是不是真能支撑结论，免得某个分支被仓库里早已废弃的旧注释带偏。

## 代码审查与疑难会诊，交接逻辑刚好相反

中心委派跑顺之后，最常问的一个实操问题是：派活时到底该给 Subagent 一个干干净净的新窗口，还是把主会话走过的历史原样带过去？

这事没有统一答案，得看子任务扮演什么角色。把日常开发里最实用的两种辅助模式——**独立代码审查**和**疑难会诊**——放在一起对比，差异就一目了然了。

先看独立代码审查。如果让同一个 Agent 自己经历五六轮报错、妥协、打补丁，写完立刻在原对话里自我审查，它可能沿用刚才的判断，漏看其他解释。这时候拉起一个干净上下文的审查 Subagent，只给它看最终的 `git diff`、关联源码和验收条件，能帮它跳出编写者的路径依赖，更容易挑出遗漏的边界条件。

不过，干净上下文并不自动保证挑刺更准。实际用起来经常会遇到另一种误报：某段代码写得绕弯子，其实是为了兼容线上存量的老数据格式，而这条背景只出现在主会话早期的讨论里，没写进派给审查者的说明。不知情的审查 Subagent 就会反复要求“把这段冗余逻辑删掉”。因此做审查交接时，要剥离的是**试错过程**，不能连**已经确认的业务约束和兼容前提**一起砍掉；面对审查意见，最终也得由掌握全局上下文的主 Agent 或开发者来甄别去留，在这里校准几次上下文松紧度很正常。

疑难会诊的逻辑则完全反过来。当主 Agent 卡在一个诡异的并发死锁或偶发测试失败上，准备调用更擅长深度推理的模型帮忙诊断时，如果只切一小段报错过去、把前因后果全丢掉，会诊模型可能重复建议主 Agent 已经排除过的常规解释。

这种场景下，需要给足与问题相关的现场信息：脱敏后的完整报错堆栈、相关代码片段，尤其是“已经试过哪几种改法、各自看到了什么现象、为什么排除了这些假设”，都得一并传过去。现在不少支持 Subagent 的编码工具在默认隔离之外保留了继承当前会话历史的 `fork` 模式，服务的就是这类延续性诊断。想让会诊真正管用，还得守住两条规矩：主 Agent 得清楚什么时候该停下来求助并提出具体问题；会诊模型发现手头证据不够时，要允许它要求补充查看某个文件或某段日志，别在信息残缺时硬猜结论。

## 读操作容易并行，共同改代码难在隐含假设

前面说的检索、审查和会诊，本质上都遵循同一个分工结构：**主 Agent 单写者，其他 Subagent 只读或提建议**。一旦越过这条线，让多个 Subagent 同时动手改一套互相关联的代码，就需要额外处理写入冲突和接口一致性。

阻碍并行改代码的，往往不是低级的语法错误，而是两边在细节上的**隐含假设冲突**。设想把一个新需求拆给两个 Subagent 同时写：一个改后端订单接口，一个改前端调用层。哪怕动手前给两边发了同一份接口草稿，真正写代码时还是会冒出几十个草稿没写细的小决定——字段为空时返回 `null` 还是空数组、409 冲突时的错误体结构怎么包、超时后由哪一层负责重试。由于子分支之间默认互不通气，主 Agent 也经常高估子分支对背景的默契度，两边各自按合理猜测写完，单看每一份代码都挺干净，合到一起跑联调却处处对不上。

靠共享文件加临时锁让平级 Agent 自己协调，在实践里也很难跑顺：一旦分支变多，锁争用和异常退出后漏释放锁就会拖垮整体进度，因此需要明确任务分工，以及锁释放和失败恢复的处理方式。所以在绝大多数日常开发任务里，只要改动还会牵动同一份数据结构或公共接口，让主 Agent 自己按顺序改代码、把周边查资料和跑检查的活分给只读 Subagent，通常比硬凑多写者省心得多。

那什么情况下才适合让多个 Subagent 同时写代码？一般是核心接口已经稳定、各模块物理边界非常清楚的时候——比如给五个互不依赖的数据源分别补齐适配器，或者按统一规范批量迁移一批独立子包。真要走多写者协作，动手前需要先把护栏搭好：

- **先冻结契约再派活**：公共接口签名、数据结构和错误约定必须在主会话里先敲定并落成文件，不允许子分支边写边改公共定义。
- **互斥划分写入范围并隔离工作目录**：按互不重叠的目录或文件分配归属，配合独立的 `git worktree` 隔开各自的工作树，避免并发编辑和本地跑单测时互相踩脏未提交的改动。
- **单一集成者兜底**：所有分支写完后，由唯一的主 Agent 负责合并代码并跑跨模块集成测试；如果某个分支中途发现公共契约非改不可，先停下来回主循环对齐，别在局部分支里私自打补丁。

## 权限边界与失败恢复的两个底线

把任务划分和协作方式理顺之后，系统真正跑在线上或本地终端里，还有两条基础设施层面的底线需要看住。

**第一条底线：上下文隔离不等于运行环境隔离。**

给 Subagent 新开一个对话窗口，隔开的只是发给模型的消息列表。在本地 CLI、IDE 或同一个云端容器里，父子任务可能仍共享文件系统、环境变量、网络出口或 MCP 凭据，具体取决于运行环境与配置。就算用了 `git worktree` 把代码目录拆开，它也只是 Git 层面的工作树隔离，挡不住子进程去读环境变量里的密钥、调内网接口或操作共享数据库。

指望在系统提示词里写一句“请勿修改生产环境”并不算权限控制。可靠的做法是分层收敛：派活摘要发给子分支前先筛掉无关密钥和敏感字段；把抓取回来的外部网页、第三方文档一律当成待核验的数据处理，防止提示词注入顺着摘要污染主会话或写入长期记忆；只读分支直接在工具注册层拿掉写入与外发工具，并在工具服务端独立校验调用权限，涉及发布、建单、打款等外部高风险动作时保留人工确认。

**第二条底线：并发异常和断点恢复要防“脑补”与“重复副作用”。**

刚引入并行 Subagent 时，并发拉起两三个只读分支就够了，同时配好最大并发数、递归深度上限和取消传递——主任务一旦取消或失败，及时停掉还在后台空转的子分支，免得一窝蜂撞上模型或外部接口的限流。

运行中难免遇到个别分支超时，或者撞上最大轮数上限被强制停机。遇到这种部分完成的情况，保留已成功分支的结果即可，但合并时必须把失败或触顶停机的分支明确标为“未覆盖”，不能因为循环正常退出就当成检查通过，更要防止主模型顺手把缺掉的那块结论自己猜出来补齐。

如果长任务接入了检查点（Checkpoint）做断点恢复，还要额外盯紧外部副作用。检查点只记录流程走到了哪一步，恢复运行时往往会从失败节点的边界重新执行。假如某个 Subagent 上一轮其实已经调通外部接口发出了通知、创建了工单或写了库，只是在等网络回执时断连，盲目重跑就会触发重复操作。凡是会改动外部世界状态的步骤，调用前都需要带上稳定的业务幂等键，恢复或重试前先查远端真实状态，状态查不清时宁可停下来等人工处理。

## 拿真实任务决定去留

公开技术博客里的评测涨幅，或是开源框架里的多角色演示，只能说明某种编排在特定题目下跑得通，没法直接折算成你手头项目的收益。

判断一个 Subagent 值不值得拆、拆完该不该留，最实在的办法是从平时真实的开发或业务记录里抽一批固定任务，锁死模型版本和预算上限，拉两组对照跑一跑：一组是配好按需加载工具与上下文的单 Agent 主循环，另一组是引入 Subagent 的版本；如果已经在给复杂系统做减法，每次也只合并或调整一个角色，方便看清变量。

对比结果时，把准确率、源码引用的真实性、长尾延迟（P95）、父子合计的 token 账单，以及人花在复核上的时间摆在一起看，顺手再模拟一两次子分支超时或返回旧快照的异常。能稳定隔离主会话噪音、明显缩短独立检索等待，或者确需收紧工具权限的地方，就把输入输出契约打磨扎实留下来；要是多绕一层委派没让结果准多少，倒把排错难度、等待时间和账单抬高了一截，趁早删掉多余角色退回主循环，系统反而更清爽。
