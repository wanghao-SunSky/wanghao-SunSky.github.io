# 写作与发布 SOP

版本：2026-11-01

一句话流程：先从收藏中选出值得解决的问题，再核查资料、补充自己的实验或项目证据，发布在 `https://wanghao-sunsky.github.io/`，最后把同一篇正文发到中文平台、在 X 发串推，并复盘。写作环节由 Agent 辅助，流程见 [writing-agent.md](writing-agent.md)。整条流程的一页总览见 [pipeline.md](pipeline.md)。

## 0. 状态与完成标准

| 状态 | 进入条件 | 完成标准 |
| --- | --- | --- |
| `captured` | 收藏到一个可能有价值的材料 | 已记录链接、主题和收藏原因 |
| `selected` | 选题评分达到要求 | 有读者、问题和新增价值 |
| `researching` | 开始查原始资料 | 关键事实都有原始出处或标为未知 |
| `drafting` | 已有一句话结论和大纲 | 文章结构完整，示例可读 |
| `verifying` | 正文完成 | 事实、代码、图、引用、隐私检查通过 |
| `published` | 网站已上线 | 线上页面、链接和基础 SEO 检查通过 |
| `distributed` | 平台版本已发布 | 记录平台链接和发布时间 |
| `reviewed` | 已到第 7 或第 30 天 | 记录结果、问题和下一步 |
| `corrected` | 发现实质错误并修正 | 页面和更正记录写明改动 |

## 1. 收集：X 收藏进入选题池

每周固定一次处理新收藏，单次 30–60 分钟。

在 `workbench/inbox/x-bookmarks.csv` 记录：

```csv
captured_at,url,author,topic,why_saved,primary_source,status,next_action
2026-11-01,https://x.com/...,@author,agent-memory,"提出记忆更新问题",https://arxiv.org/...,captured,"找原论文"
```

处理规则：

- 先找原始来源，例如论文、官方文档、源码或作者原文。
- 只把帖子作为线索，不把转述当作事实来源。
- 收藏原文不进入公开仓库；公开文章只引用必要的短内容并附链接。

## 2. 选题评分

每项 0–2 分，总分 10 分。达到 7 分进入写作；5–6 分保留观察；低于 5 分归档。

| 维度 | 0 分 | 1 分 | 2 分 |
| --- | --- | --- | --- |
| 读者需求 | 说不清谁需要 | 有大概人群 | 能写出具体读者和问题 |
| 新增价值 | 只能复述 | 能补充解释 | 有实验、代码、比较或项目经验 |
| 证据可得 | 只有二手观点 | 有部分原始资料 | 原始资料和可验证材料充足 |
| 主线相关 | 偏离 Agent 工程 | 间接相关 | 能放进现有主题体系 |
| 面试价值 | 难以展示能力 | 能体现理解 | 能讲清问题、取舍、证据和局限 |

热点只是加分理由，不能单独决定选题。

## 3. 写研究简报

使用 [研究简报模板](../templates/research-brief.md)。写正文前必须回答：

- 读者是谁，他们现在卡在哪里？
- 文章最终要证明或解释哪一个结论？
- 哪些是事实，哪些是推断，哪些仍未知？
- 我要增加什么：代码、实验、方案对比还是项目复盘？
- 哪些来源是原始资料，访问日期是什么？

写不出一句话结论时，先缩小题目。

## 4. 写作

使用 [文章模板](../templates/article.md)。正文推荐顺序：

1. 开头说明问题和结论。
2. 用一个具体场景说明为什么这个问题重要。
3. 解释机制，必要时给出流程图、伪代码或最小示例。
4. 比较可选方案，写清楚代价。
5. 给出实验、代码或项目证据。
6. 写明适用边界和未解决问题。
7. 给出来源和延伸阅读。

写作要求：

- 动笔前先做搜索词研究（见 [seo-distribution.md](seo-distribution.md)），主关键词进标题、H1、描述和首段，相关词进 2–3 个小标题。
- 搜索词研究后先选讲法，正文定稿后再定标题、封面文字和开头，规则见 [title-cover-intro.md](title-cover-intro.md)。
- 默认读者是用过 AI 编程工具、没读过 Agent 框架源码的开发者和技术爱好者；先写读者读完能复述的一句话，再写 300 字短版，最后扩写。
- 通用开发词直接用，项目自造的概念写成“中文名（英文原名）”加一句说明；用真实场景和源码规则举例，不用无关的生活类比；小标题写成读者的问题。
- 边界集中写在一个小节；关键源码链接就近放，其余放文末。
- 无上下文的读者测试通过后才能进入核查完成状态。完整流程见 [writing-agent.md](writing-agent.md)，写法样本见 [style-reference.md](style-reference.md)。
- 一段只讲一个意思。
- 不用“彻底解决”“全面超越”等无法验证的说法。
- 示例代码只保留说明问题所需的部分，完整代码放到 `examples/`。
- 图片中的流程、数值和标签必须与正文一致。

## 5. 核查

使用 [发布检查清单](../templates/publish-checklist.md)。

最低要求：

- 关键定义、数字、公式和结论都已对照原始资料。
- 代码按 README 从空环境运行过；不能运行时，正文写明未运行。
- 实验写明模型、版本、数据、参数、样本量和结果日期。
- 引用内容不超过说明观点所需的长度，并附原文链接。
- 未发现密钥、个人信息、公司保密信息和私有路径。
- AI 辅助只用于整理、改写或检查；最终事实由作者核对。

存在实质性未核实内容时，状态保持 `verifying`，不发布。

## 6. 发布到网站（wanghao-sunsky.github.io）

1. 从 `main` 新建 `post/<slug>` 分支。
2. 添加文章、图片和示例代码。
3. 本地运行内容检查、链接检查、示例测试和构建。
4. 在桌面和手机预览中完整读一遍。
5. 提交 Pull Request，确认 CI 通过。
6. 合并后等待 GitHub Pages 部署。
7. 检查线上页面：标题、描述、规范地址、目录、图片、代码块、内链和分享卡片。页面样式按 [site-design.md](site-design.md)。
8. 在 Search Console 检查该地址并请求编入索引；IndexNow 由 CI 自动提交；百度用 API 推送。细节见 [seo-distribution.md](seo-distribution.md)。

提交和请求编入索引都不保证收录或排名。

## 7. 平台分发

网站上线 1–2 天后再发平台。掘金、知乎、CSDN 发同一篇正文，只换标题和文末一行；不为每个平台单独改写。各平台规则和核实来源见 [platforms.md](platforms.md)，发文前再看一眼发布页提示。

| 平台 | 发什么 | 只改这些 |
| --- | --- | --- |
| 掘金 | 网站正文原样 | 标题偏源码和做法；文末“首发于”加网站链接 |
| 知乎 | 网站正文原样，发成专栏文章 | 标题写成读者会问的问题；文末一条链接，标题和简介不放链接 |
| CSDN | 网站正文原样，选“原创” | 标题带主关键词和项目名；文末一条链接 |
| X | 没订阅 Premium 发不了长文，用 300 字短版改成 3–6 条串推 | 最后一条放文章链接 |
| GitHub | README 文章索引、示例代码 README | 链接到网站文章 |

平台标题按 [title-cover-intro.md](title-cover-intro.md) 定。正文里的站内相对链接发之前换成完整地址；图片在平台编辑器里重新上传，避免外链图挂掉。

分发规则：

- 正文本身要能独立解决读者问题，不只写“详见链接”。
- 网站先上线并在 Search Console 请求编入索引，让搜索引擎先见到网站版本。
- 文末统一写“首发于 <网站链接>，示例代码见 <仓库链接>”。
- 每个平台只发一次同一内容；后续更新以“更新说明”形式发布。
- 不买量、不互赞、不批量发同质内容、不在无关讨论下刷链接。

## 8. 面试复用

发布后 24 小时内，使用 [面试案例卡模板](../templates/interview-card.md) 写一张私有卡片。

合格标准：

- 能在 60 秒内讲清问题和结论。
- 能在 5 分钟内讲清方案、取舍、证据和局限。
- 能回答至少 5 个追问，答案能回到代码、实验或资料。
- 区分“读过”“做过实验”“在项目中实现过”“在生产环境验证过”。

## 9. 复盘

### 第 7 天

记录：

- 网站访问、平台阅读、GitHub 访问。
- 有价值的评论和问题。
- 是否收录；如有数据，记录搜索词。
- 文章中读者最常误解的部分。

### 第 30 天

只选择一个主要问题处理：

| 现象 | 处理 |
| --- | --- |
| 曝光低 | 检查渠道是否匹配，标题是否说明具体问题 |
| 点击低 | 改写标题、描述或平台开头，突出具体结果 |
| 阅读后反馈少 | 增加示例、练习或更清楚的结论 |
| 搜索有曝光但点击低 | 检查标题和描述是否匹配搜索词 |
| 发现事实错误 | 优先修正，并写入更正记录 |

不同平台的数据口径分别记录，不把浏览量、访问量和 Star 直接相加。

## 10. 更新与纠错

- 小改动：错别字、排版、无关结论的链接更新，可直接修改。
- 实质更正：改变事实、结论、代码结果或适用范围时，在文章底部写明日期和改动，并加入 `docs/corrections.md`。
- 过期内容：保留原地址，在开头说明已过期，并链接新文章。
- 删除内容：只在侵权、隐私或安全问题时删除；删除后保留必要的说明或跳转。

## 11. 节奏

首月目标：

- 第 1 周：确定域名、仓库、网站模板和 5 个主题。
- 第 2–3 周：完成 1 篇实验或项目文章。
- 第 4 周：完成 1 篇技术解读或新技术判断文章，并完成首轮复盘。

之后按每两周 1 篇深度文章推进。时间不足时延期，不降低核查标准。
