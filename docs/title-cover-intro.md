# 标题、封面和开头

版本：2026-11-01。方法改编自 dbs-title-cover-intro（dbskill v3.1.0，本地路径 `~/.gemini/dbskill/skills/dbs-title-cover-intro/`），“先定选题、再写标题封面和开头”的顺序源自“dontbesilent 内容方法论”。原 skill 面向短视频和小红书，这里只取方法，按技术文章和 SEO 改写。

## 先定讲法，再写标题

标题、封面和开头都在替选题拉读者。讲法没定就写标题，标题只能靠夸大吸引人，读者点进来发现对不上就走了。

搜索词研究之后、写简报之前，Agent 给作者一份讲法菜单：

- 最多 4 个讲法。第 1 个用素材原来的说法，后面每个比前一个面向更多的人。
- 每个讲法写清：一句话讲什么；改了哪个词或加了什么信息；谁会感兴趣；正文哪一节能撑住，不够时还要补什么；有明显风险时写一句会发生什么。
- 推荐一个，写一句理由。
- 最多问作者 2 个问题，只问能让读者更相信的经历或数字，例如“这个 Agent 你在自己项目里跑过几天”“改过几个仓库”。

让讲法面向更多人的办法：加上作者的经历或数字；换成读者的日常说法；挂到读者已经关心的大问题上，例如“让 AI 自己提 PR 安不安全”；换一群读者，例如从“关注 DeepSeek 的人”换到“在搭自动编码 Agent 的人”。

每扩大一次都检查四件事，过不去就退回上一个：

| 检查 | 问题 |
| --- | --- |
| 正文兑现 | 正文能不能讲清这个讲法承诺的东西 |
| 读者对不对 | 吸引来的人是不是主线读者：做 Agent、用 AI 编程工具的开发者 |
| 评论会不会跑偏 | 评论会不会只吵“国产和国外谁强”这类和正文无关的事 |
| 像不像空话 | 离具体项目太远时，开头能不能很快回到项目 |

## 三种标题分工

| 位置 | 服务谁 | 写法 |
| --- | --- | --- |
| 网站标题（`title`、H1） | 搜索 | 主关键词靠前，写清问题或结论，30 字以内。用第 1 个讲法或最贴近搜索意图的讲法 |
| 平台标题 | 推荐流和平台站内搜索 | 用作者选定的讲法。掘金偏源码和做法；知乎写成读者会问的问题；CSDN 主关键词和项目名都要有；X 首句写发生了什么、为什么值得看 |
| 封面文字 | 信息流里一眼看懂 | 用在网站 OG 图、掘金和知乎头图、X 配图上，规则见下一节 |

三者共用一个讲法，但各给不同信息：标题给问题或判断，封面给数字、场景或具体结果，开头给“它是什么”和读者为什么该关心。同一句话不在三处重复。

平台标题只在平台、读者或搜索词不同的时候才改，不为了显得做过适配造一堆意思差不多的标题。

## 封面文字

- 每行最多 6 个字，这是硬限制。换过更短的说法仍看不懂，才允许 7 个字，交付时写明是哪一行、为什么。8 个字以上重写。
- 字母、数字、符号每个算 1 个字，“AI”算 2 个，“DeepSeek”算 8 个。项目名太长时放进标题，封面写它做了什么。
- 默认 3 行，一般不超过 4 行。
- 写完把几行连成一句读，检查主语有没有混。作者的经历和对别人的判断同时出现时，作者那句带上“我”。
- 用具体对象、数字、动作和结果；不用“真相”“底层逻辑”“干货”这类空词。
- 封面图上只放封面文字和固定的站点名，站点名不算第二个标题。
- 版式按 [site-design.md](site-design.md) 的 OG 图规则。

## 开头

开头要当成一份试用装：读者没看标题也能懂，读完前两句知道这篇讲什么、值不值得读。技术文章的开头还要满足 SEO。

- 第一句讲读者关心的问题或发生了什么，紧接着亮出依据：作者读了哪个版本的源码、跑了几次实验、在项目里用了多久。
- 前 100 字内出现主关键词，说清“它是什么、能干什么”。
- 第一段结尾说清这篇回答哪几个问题，第二段直接进入正文，不绕回背景。
- 不列“第一、第二”，不写“随着 AI 的发展”这类铺垫。
- 开头说的每件事，正文都要有对应的一节。

## 兑现检查

标题、封面和开头写完后逐项过，任何一项不过就改：

| 项目 | 问题 |
| --- | --- |
| 事实 | 标题、封面、开头里的每个说法，正文和核查表里都有出处 |
| 兑现 | 读者被标题吸引来想知道的东西，正文哪一节给了 |
| 一致 | 标题、封面、开头是同一个讲法 |
| 分工 | 三处各给不同信息，没有同一句话出现三遍 |
| 独立 | 陌生人只看标题或只看封面，能认出主题和对象 |
| 不夸大 | 没有“最强”“颠覆”“彻底”；推断写成推断 |
| 搜索 | 网站标题、描述、首段含主关键词 |

## 示例：DeepSeek SuperAgent 那篇

完整记录在私有工作区 `distribution/deepseek-superagent-source/title-cover-intro.md`，这里摘结论。

讲法菜单：

1. DeepSeek SuperAgent 是什么，从源码看它怎么在 GitHub 上接活。读者是关注 DeepSeek 新项目的开发者，人少但正在搜。
2. 让 AI 自己接 Issue、提 PR，难在代码之外的三件事，以 DeepSeek SuperAgent 为例。读者扩到在搭或想用自动编码 Agent 的人，正文三节都能撑住。
3. 公开仓库里的 AI Agent，怎么防止路人一句评论就让它乱改代码。读者更多，但正文只有“谁的消息算命令”一节讲这个，评论容易跑到提示词注入的泛泛讨论。

推荐：网站标题用 1，因为搜索的人用的是项目名；平台标题、封面和开头用 2，因为正文的三节正好是它说的三件事。

| 位置 | 文字 |
| --- | --- |
| 网站标题 | DeepSeek SuperAgent 是什么？从源码看它怎么在 GitHub 上接活 |
| 掘金 | DeepSeek SuperAgent 源码解读：让 AI 自己提 PR，难在代码之外的三件事 |
| 知乎 | 让 AI Agent 自己接 Issue、提 PR，最难的部分是什么？从 DeepSeek SuperAgent 源码看 |
| CSDN | DeepSeek SuperAgent（dsh-superagent）架构解析：准入、工单和重启恢复 |
| X 首句 | DeepSeek 开源了一个会自己接 Issue、提 PR 的 Agent。我读了源码，改代码交给模型，代码花篇幅的是另外三件事。 |
| 封面 | 让 AI 提 PR／难在代码之外／谁的话算命令 |

封面连读：“让 AI 提 PR，难在代码之外：谁的话算命令。”只有一个主语，三行各 6 个字。
