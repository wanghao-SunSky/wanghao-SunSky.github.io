## 写法规则

### 开头

- 第一段说清发生了什么、对读者有什么用。不从定义开始。
- 第二段抛出难点或反差，告诉读者接下来要回答哪几个问题。
- 不写“今天聊聊”“你可能不知道”这类空开头。

### 讲解

- **通用开发词直接用。** Issue、PR、CI、分支、worktree、会话、提示词，读者都用过，不加解释。
- **项目自造的概念写成“中文名（英文原名）”**，紧跟一句话说它在项目里管什么，例如“授权记录（Mandate）：记下谁、在哪个仓库、允许它做什么”。后文统一用中文名。
- **用真实例子。** 直接讲真实场景（在 Issue 里 @ 它修 bug）、源码规则（命令超过 5 秒转后台）和数字。不用维修店、餐厅这类和技术无关的生活类比，它们会把技术内容替换掉。
- **对比只用同领域的东西。** 真实例子讲不清时，拿读者用过的技术对比，例如“像 Linux epoll”“和 GitHub Actions 的重试一样”。
- **一个场景讲到底。** 选一个真实场景串起全文，不在每节换场景。按文档推演的场景要说明是推演。
- **小标题同时是读者的问题和搜索词**，例如“DeepSeek SuperAgent 是什么”“PR 里有人插话怎么办”。
- 能用表格对比的不写成长段落。
- 有真实数字就写数字，没有就不编。

### SEO

- 标题、H1、描述、首段前 100 字都含主关键词；2–3 个小标题含相关词。关键词来自动笔前的联想词研究，不凭感觉起。
- 首段先回答“它是什么、能干什么”，搜索进来的人第一屏就能拿到答案。
- 产品名有同名干扰时带上区分词，例如写“DeepSeek SuperAgent”，不单写“SuperAgent”。
- 关键词自然出现即可，不在一段里重复堆。

### 边界和证据

- 事实核查照做，核查表放私有区。
- 正文只写会改变读者判断的边界，集中在一个“用之前要知道的”小节，用大白话写，不写“不能写成……”这类给核查人看的句子。
- 关键源码和文档链接放在对应句子旁边，读者想核对时不用翻到文末；其余放文末“源码对照”。
- 区分“代码和文档是这么写的”和“我测过”。没测过就说一次，不在每段重复。

### 结尾

- 给读者能带走的 2–3 条做法。
- 不写祝福、口号或升华。
